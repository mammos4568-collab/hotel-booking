## ข้อมูลที่ใช้

| ตาราง | ใช้ทำอะไร |
|---|---|
| `rooms` | ประเภทห้อง: `total_rooms` = มีห้องจริงกี่ห้อง, `base_price_per_night`, `max_guests` |
| `room_inventories` | (ไม่บังคับ) ปรับรายวัน: `price` = ราคาวันนั้น (สุดสัปดาห์/ปีใหม่แพงขึ้น), `available_rooms` = เปิดขายกี่ห้องในวันนั้น |
| `bookings` | การจอง 1 แถว = 1–5 ห้องของประเภทเดียวกัน (`num_rooms` เพิ่มใน `03-booking.sql`) · ช่วงวัน `[check_in_date, check_out_date)` ไม่นับคืนวันเช็กเอาต์ |
| `payments` | ประวัติจ่ายเงินจำลอง (เก็บแค่ 4 หลักท้ายของบัตร) — เพิ่มใน `03-booking.sql` |
| `favorites` | รายการโปรด `(user_id, property_id)` เป็น PRIMARY KEY คู่ — เพิ่มใน `03-booking.sql` |

สถานะใน `bookings` (ข้อความเดียวกับข้อมูลของทีม):

| `payment_status` | `booking_status` | หน้าเว็บแสดงเป็น |
|---|---|---|
| `Pending` (ยังไม่เกิน 15 นาที) | `Confirmed` | รอชำระเงิน (`awaiting_payment`) |
| `Pending` (เกิน 15 นาที) / `Expired` | `Confirmed` / `Cancelled` | หมดเวลาชำระ (`expired`) |
| `Paid` | `Confirmed` | ยืนยันแล้ว (`confirmed`) → เลยวันเช็กเอาต์ = `completed` |
| `Refunded` / `Pending` / `Failed` | `Cancelled` | ยกเลิกแล้ว (`cancelled`) — `Failed` = จ่ายผิดครบ 5 ครั้ง |

## 1. `availability.js` — หัวใจของระบบ

**ห้องว่างของคืน d** = ความจุคืนนั้น − จำนวน**ห้อง**ที่ถูกจอง (การจองที่ "ยังกินห้อง" และครอบคืน d)

- ความจุคืนนั้น = `total_rooms` (หรือน้อยกว่า ถ้า `room_inventories.available_rooms` วันนั้นตั้งไว้)
- การจองครอบคืน d เมื่อ `check_in_date <= d AND check_out_date > d`
  → ใช้ `<=` กับ `>` เพราะไม่นับคืนวันเช็กเอาต์: คนหนึ่งเช็กเอาต์วันที่ 12 อีกคนเช็กอินวันที่ 12 ได้
- "ยังกินห้อง" = `booking_status <> 'Cancelled'` และไม่ใช่การจองค้างชำระที่เกิน 15 นาทีแล้ว

**ห้องว่างทั้งทริป** = ค่า**น้อยที่สุด**ของทุกคืน (ต้องว่างครบทุกคืนถึงจะจองได้)
**ราคารวม** = ผลรวมราคารายคืน (`room_inventories.price` ถ้ามี ไม่งั้น `base_price_per_night`)

```sql
-- แถวละ 1 คืน ของประเภทห้องหนึ่ง ($2 = checkIn, $3 = checkOut)
SELECT n.night,
       COALESCE(inv.price, r.base_price_per_night) AS price,
       LEAST(r.total_rooms, COALESCE(inv.available_rooms, r.total_rooms))
         - (SELECT COALESCE(SUM(b.num_rooms), 0) FROM bookings b
             WHERE b.room_id = r.room_id
               AND b.check_in_date <= n.night AND b.check_out_date > n.night
               AND <การจองที่ยังกินห้อง>) AS available
FROM rooms r
CROSS JOIN (SELECT $2::date + i AS night
              FROM generate_series(0, $3::date - $2::date - 1) AS i) n
LEFT JOIN room_inventories inv ON inv.room_id = r.room_id AND inv.date = n.night
WHERE r.room_id = $1;
```

**ทำไมใช้ `SUM(num_rooms)` ไม่ใช่ `COUNT(*)`:** การจองหนึ่งจองได้หลายห้อง — ถ้านับจำนวนแถว
การจอง 2 ห้องจะถูกนับเป็น 1 แล้วระบบจะขายห้องเกินจริง

**ทำไมต้องนับรายคืน ไม่นับแค่ "จำนวนการจองที่ทับช่วง":** สมมติมี 2 ห้อง การจอง A = 1–2, B = 2–3
ถ้าขอ 1–3 การนับแบบหยาบจะเห็น 2 รายการทับ → ตอบว่าเต็ม ทั้งที่แต่ละคืนถูกจองแค่ 1 ห้อง (ยังว่าง 1)

ฟังก์ชันในไฟล์: `getNightlyRates()` (รายคืนของห้องเดียว — ใช้ตอนจองและสรุปราคา),
`roomAvailabilitySql()` (สรุปทุกประเภทห้อง — หน้าค้นหา/หน้าโรงแรมใช้เป็น CTE), `lockRoomType()`

## 2. `POST /api/bookings` — กันจองซ้อนด้วย transaction + row lock

```json
{ "roomId": 25, "checkIn": "2026-11-13", "checkOut": "2026-11-15", "guests": 5, "rooms": 2,
  "guestName": "...", "guestEmail": "...", "guestPhone": "...", "specialRequests": "..." }
```

ขั้นตอน (ใน `server/src/modules/booking/routes.js`):

1. ตรวจ input **ก่อน** เปิด transaction (วันที่, ไม่ย้อนหลัง, ไม่เกิน 30 คืน, จำนวนคน, อีเมล)
2. `const client = await pool.connect()` แล้ว `BEGIN` — ทุกคำสั่งต้องผ่าน `client` ตัวเดียวกัน
   (ถ้าใช้ `pool.query()` แต่ละคำสั่งอาจได้คนละ connection ทรานแซกชันจะไม่ครอบ)
3. 🔒 `SELECT ... FROM rooms WHERE room_id = $1 FOR UPDATE` — **ล็อกแถวประเภทห้อง**
4. นับห้องว่างรายคืน (หลังได้ล็อกแล้ว) → ว่างน้อยกว่า `rooms` ตอบ **409**
   (`ห้องประเภทนี้เต็มในช่วงวันที่เลือก` / `ว่างไม่พอ (เหลือ N ห้อง)`)
   · ตรวจความจุ: `guests <= max_guests × rooms` และ `rooms <= guests` (ทุกห้องต้องมีคนพัก) ไม่ผ่านตอบ **400**
5. คำนวณราคารวมจากราคารายคืนใน DB × จำนวนห้อง — **ไม่เชื่อราคาที่ client ส่งมา**
6. `INSERT` (สถานะ `Pending`) → `COMMIT` · พังตรงไหน `ROLLBACK` และ `client.release()` ใน `finally`

**ทำไมต้อง `FOR UPDATE`:** ถ้าสองคนกดจองห้องสุดท้ายพร้อมกัน ทั้งคู่จะนับเห็น "ว่าง 1" แล้ว INSERT
สำเร็จทั้งคู่ = จองเกิน (race condition แบบเดียวกับ critical section ในวิชา OS)
`FOR UPDATE` ทำหน้าที่เหมือน **mutex ต่อประเภทห้อง**: คำขอที่สองต้องรอจนคนแรก COMMIT
แล้วค่อยนับใหม่ — ใน READ COMMITTED แต่ละคำสั่งเห็นข้อมูลที่ commit แล้วล่าสุด
คนที่สองจึงเห็นการจองของคนแรกและได้ 409 แทน

**ล็อกแค่ประเภทห้องที่จอง** ประเภทอื่น/โรงแรมอื่นจองพร้อมกันได้ตามปกติ ไม่ช้าลง

**ตาข่ายระดับ DB เพิ่มเติม** (`03-booking.sql`): `CHECK (check_out_date > check_in_date)`,
`CHECK (num_guests >= 1)`, `CHECK (num_rooms BETWEEN 1 AND 5)` — ข้อมูลผิดแน่ๆ เข้าตารางไม่ได้แม้โค้ดพลาด

**เลขที่การจอง** `AGD-ปี-เลขลำดับ` ขอเลขจาก sequence ของ `booking_id` ก่อน INSERT จึงไม่ซ้ำแน่นอน

## 3–5. endpoint ที่เหลือ

| Endpoint | ทำอะไร | ต้องเช็ก / ตอบกลับ |
|---|---|---|
| `GET /api/bookings/quote?roomId&checkIn&checkOut&guests&rooms` | สรุปราคารายคืน (ต่อห้อง) + ราคารวมทุกห้อง + ห้องว่าง (หน้า checkout) | ไม่ต้องล็อกอิน · บอก `enoughRooms`, `capacityError` |
| `POST /api/bookings/:id/pay` | `INSERT payments` + `payment_status = 'Paid'` | ของ `req.user.id` · รอชำระอยู่ · ไม่หมดเวลา · `FOR UPDATE` แถวการจองกันกดจ่ายซ้ำ |
| `GET /api/bookings/me` | รายการจองของตัวเอง + โรงแรม/ห้อง/การชำระเงิน | — |
| `GET /api/bookings/:id` | รายละเอียด 1 รายการ | ไม่ใช่ของตัวเอง **403** · ไม่มี **404** |
| `POST /api/bookings/:id/cancel` | `booking_status = 'Cancelled'` (จ่ายแล้ว → `Refunded`) | ของตัวเอง · รอชำระ = ยกเลิกได้ตลอด (แค่ปล่อยห้อง) · จ่ายแล้ว = ก่อนวันเช็กอินเท่านั้น (`canCancel` ใน `lib/bookings.js`) · `FOR UPDATE` กันชนกับการจ่ายเงิน |

ชำระเงิน (จำลอง): ตรวจเลขบัตรด้วย Luhn, วันหมดอายุ, CVC · เก็บแค่ 4 หลักท้าย
**รับเฉพาะบัตรทดสอบ** `4242 4242 4242 4242` / `5555 5555 5555 4444` ผ่าน · `4000 0000 0000 0002` ถูกปฏิเสธ (402)
เลขอื่นตอบ 400 — เว็บขึ้น host จริงแล้วอาจมีคนเผลอพิมพ์บัตรจริง: หน้าเว็บตรวจก่อนส่ง (เลขบัตรไม่ออกจากเบราว์เซอร์)
server ตรวจซ้ำ และการจ่ายพลาดด้วยเลขที่ไม่ใช่บัตรทดสอบไม่เก็บแม้แต่ 4 หลักท้าย · ฟอร์มปิด autofill บัตรของเบราว์เซอร์
จ่ายหลังหมดเวลา 15 นาที → ปิดการจองเป็น `Cancelled/Expired` แล้วตอบ 409 ให้จองใหม่

**ทุก endpoint กรองด้วย `req.user.id`** ไม่งั้นใครก็ดูหรือยกเลิกการจองคนอื่นได้


## 8. กันการใช้งานในทางที่ผิด (สแปม / คำหยาบ)

| กันอะไร | ทำอย่างไร | ไฟล์ |
|---|---|---|
| ยิงคำขอรัวๆ | rate limit **10 คำขอ/นาที ต่อผู้ใช้** ที่ สร้างการจอง / จ่ายเงิน / ยกเลิก — เกินได้ **429** + `Retry-After` | `lib/rateLimit.js` |
| กักห้อง (จองค้างไว้ไม่จ่าย) | รอชำระพร้อมกันได้ **ไม่เกิน 3 รายการต่อคน** — เกินได้ 429 | `modules/booking/routes.js` |
| สุ่มเลขบัตร (card testing) | จ่ายไม่สำเร็จนับไว้ในตาราง `payments` (`status = 'Failed'`) ครบ **5 ครั้ง** ยกเลิกการจองทันที | `modules/booking/routes.js` |
| คำหยาบในคำขอพิเศษ | ตัดคำไทยด้วย `Intl.Segmenter` แล้วเทียบทั้งคำ + จับการเลี่ยง (`ค.ว.ย`, `ควยยย`, `f*ck`, `sh1t`) → 400 | `lib/moderation.js` |
| คำหยาบในความคิดเห็นรีวิว | ตัวกรองเดียวกัน ครอบหน้า module รีวิว `rejectProfanity('comment', ...)` ทั้งเขียนใหม่ (POST) และแก้ไข (PUT) → 400 — ไม่ต้องแก้ไฟล์ `modules/reviews/` | `index.js` + `lib/moderation.js` |

**rate limit แบบ fixed window:** นับคำขอของแต่ละ user id ในหน้าต่าง 60 วินาที เกินก็ตอบ 429
เก็บตัวนับในหน่วยความจำของ server (restart แล้วนับใหม่) — ถ้าวันหนึ่งรันหลาย server ต้องย้ายไปเก็บที่ Redis/DB

**ทำไมเพดาน "รอชำระ 3 รายการ" ต้องล็อกแถวผู้ใช้ (`SELECT ... FROM users ... FOR UPDATE`):**
ถ้าไม่ล็อก คนเดียวกันยิง 6 คำขอพร้อมกัน ทุกคำขอจะนับเห็น "0 รายการ" แล้วผ่านหมด (race condition เดียวกับเรื่องห้อง)
ล็อกแล้วคำขอของคนเดียวกันต้องต่อคิว — ทดสอบแล้วได้ 201 พอดี 3 ที่เหลือ 429
ลำดับการล็อกเหมือนกันทุกคำขอ (**ผู้ใช้ → ประเภทห้อง**) จึงไม่เกิด deadlock

**ทำไมต้องตัดคำก่อนกรองคำหยาบ:** ภาษาไทยไม่เว้นวรรค ถ้าใช้ `includes()` ตรงๆ
"สัดส่วน" จะติดคำว่า "สัด" และ "หีบ" จะติดคำว่า "หี" — ตัดคำแล้วเทียบทั้งคำจึงไม่ติดคำปกติ

ทดสอบ: `node server/test/protection.js`

## 11. Deploy (Docker production)

- `Dockerfile` แบบ multi-stage: build หน้าเว็บด้วย Vite แล้ว image สุดท้ายมีแค่ dependency ของ server + `client/dist`
  Express เสิร์ฟทั้ง API และหน้าเว็บจาก container เดียว (`SERVE_CLIENT=true` ใน `server/src/index.js`)
- `docker-compose.prod.yml` = PostgreSQL + แอป · ฐานข้อมูลไม่เปิดพอร์ตออกนอกเครื่อง · รอฐานข้อมูลพร้อมก่อนเปิดแอป
- ความลับอยู่ใน `.env.production` (ไม่ commit) — ตัวอย่างที่ `.env.production.example`
- `NODE_ENV=production` ทำให้คุกกี้ล็อกอินเป็น `Secure` → ใช้งานจริงต้องเป็น HTTPS (ยกเว้น localhost)
  อยู่หลัง reverse proxy ให้ตั้ง `TRUST_PROXY=1` ไม่งั้น rate limit จะนับทุกคนเป็น IP เดียวกัน
- เข้าสู่ระบบด้วย Google / GitHub: compose ส่ง Client ID / Secret จาก `.env.production` เข้า container
  และต่อ callback เป็น `<PUBLIC_URL>/api/auth/<เจ้า>/callback` ให้เอง (หน้าเว็บกับ API อยู่โดเมนเดียวกัน)
  — ช่องไหนเว้นว่างจะปิดช่องทางนั้น กดแล้วหน้าเว็บบอกว่ายังไม่เปิด (เดิม production ไม่ได้ส่งค่าเหล่านี้เข้า container เลย)
- ทดสอบแล้วบนเครื่อง: หน้าเว็บ/ลิงก์ลึก (`/hotels/7`), API, สมัครสมาชิก, ผู้ช่วย, header ความปลอดภัย,
  ไฟล์ `/assets` cache 1 ปี, เรียก API จากโดเมนอื่นได้ 403
- **HTTPS บน VPS** (`--profile https`): Caddy (`Caddyfile`) ขอใบรับรองฟรีจาก Let's Encrypt + ต่ออายุเอง,
  redirect http → https, ส่ง HSTS, ซ่อน header `Server` / `Via`, ไม่เก็บ access log · โดเมนมาจาก `PUBLIC_URL` ค่าเดียวกับแอป
- แอปผูกพอร์ตกับ `127.0.0.1` — บน Linux พอร์ตที่ Docker เปิดแบบ `0.0.0.0` ทะลุ ufw ได้ (http ธรรมดาจะหลุดออกอินเทอร์เน็ต)
- ทดสอบบนเครื่องด้วย `PUBLIC_URL=https://localhost` (Caddy ออกใบรับรองภายในให้ localhost) แยก project ไม่แตะข้อมูลจริง:
  `/api/health` ผ่าน https, http → 308 ไป https, คุกกี้ล็อกอินได้ `HttpOnly; SameSite=Lax; Secure`, Origin อื่นได้ 403,
  `server/test/payment-methods.js` ผ่านทุกข้อผ่าน Caddy
- ขั้นตอนขึ้น VPS ทีละขั้น + เช็กลิสต์หลังขึ้นเว็บ: `docs/deploy-vps.md`

## 12. ชำระเงินจริงผ่าน Opn Payments (โหมดทดสอบ) — TrueMoney + PromptPay

ตั้ง `OMISE_SECRET_KEY` (key ทดสอบ `skey_test_…`) ใน `server/.env` = TrueMoney และ PromptPay วิ่งผ่าน gateway จริง · ไม่ตั้ง = แบบจำลองเหมือนเดิม
(บัตรยังเป็นแบบจำลอง) · ฐานข้อมูล: `db/06-payment-gateway.sql` (เพิ่ม `payments.gateway_charge_id`) — PromptPay ใช้ตารางเดิม ไม่ต้องเพิ่มไฟล์ใน `db/`

ขั้นตอน TrueMoney:
1. หน้าชำระเงินกด "ไปยืนยันกับ TrueMoney" → `POST /api/bookings/:id/pay` `{ method: 'truemoney' }`
   server สร้างรายการที่ Opn (`POST /charges` · `source[type]=truemoney_jumpapp` · ยอดเป็นสตางค์) บันทึก `payments`
   สถานะ `Pending` พร้อม `gateway_charge_id` แล้วตอบ `{ redirectUrl }`
2. ลูกค้ายืนยันในแอป TrueMoney (โหมดทดสอบ: หน้าของ Opn ให้กด Successful / Failed) → Opn พากลับมาที่ `/checkout/pay/:id?gateway_return=1`
3. หน้าเว็บเรียก `POST /api/bookings/:id/pay/verify` → server **ดึงรายการจาก Opn เอง** (ไม่เชื่อ URL ที่พากลับมา) แล้วตัดสิน
   - สำเร็จ + การจองยังรอชำระ → `Paid`
   - สำเร็จ แต่หมดเวลาถือห้อง/ถูกยกเลิกไปแล้ว → **คืนเงินทันที** (ห้องอาจถูกคนอื่นจองไปแล้ว)
   - ไม่สำเร็จ → นับเป็นการจ่ายพลาด (ครบ 5 ครั้งยกเลิกการจอง) · ยังรอผล → หน้าเว็บถามซ้ำทุก 3 วินาที
   - body `{ method: 'truemoney' }` = ตรวจรายการ TrueMoney ล่าสุดของการจองนี้ (ไม่ส่ง = รายการล่าสุดของทุกวิธี)
4. webhook `POST /api/bookings/gateway/webhook` (ตั้งใน dashboard ของ Opn ตอน deploy) — ลูกค้าจ่ายแล้วปิดแอปไม่กลับมา ระบบก็ยังได้ผล
   ใช้แค่รหัสรายการจาก webhook แล้วถาม Opn เอง → ปลอม webhook มาก็ทำอะไรไม่ได้

จุดที่ต้องอธิบายได้ตอนพรีเซนต์:
- **ล็อกแถวการจอง (FOR UPDATE) ทุกทางที่อัปเดตผล** — หน้าเว็บกับ webhook อาจมาพร้อมกัน คนที่สองเห็นว่าไม่ใช่ `Pending` แล้ว
  จึงไม่บันทึก/ไม่คืนเงินซ้ำ (ฟังก์ชันเดียว `applyGatewayCharge()` ใช้ร่วมกันทุกทาง)
- **กดจ่ายซ้ำไม่สร้างรายการซ้ำ** — มีรายการ `Pending` อยู่ ใช้ลิงก์เดิม (กันโดนตัดเงินสองครั้ง)
- **ยกเลิกการจองที่จ่ายผ่าน Opn → สั่งคืนเงินที่ Opn ก่อนแก้ฐานข้อมูล** ถ้าคืนไม่สำเร็จ ROLLBACK ทั้งหมด
  (`cancelBooking()` ลูกค้าและหลังบ้านใช้ร่วมกัน) และถาม Opn ก่อนว่าคืนไปแล้วหรือยัง กันคืนซ้ำ
- secret key อยู่ที่ server เท่านั้น · ส่งให้ Opn แค่ยอดเงิน + เลขที่การจอง ไม่มีข้อมูลส่วนตัว
- ยอดต่อครั้ง ฿20–฿50,000 (ข้อจำกัดของ TrueMoney ที่ Opn) ตรวจก่อนส่ง

### PromptPay ผ่าน Opn — ตรวจเงินเข้าอัตโนมัติ (ไม่ต้องอัปสลิป ไม่มีใครต้องกดยืนยัน)

ทำไมต้องผ่าน Opn: โอนพร้อมเพย์เข้าบัญชีส่วนตัว (ข้อ 13) ธนาคารแจ้งแค่เจ้าของบัญชีในแอป ไม่มีอะไรส่งกลับมาที่เว็บ และ QR แบบนั้น
ไม่มีเลขอ้างอิงการจอง → เว็บรู้เองไม่ได้ว่าเงินเข้า · QR ของ Opn ผูกกับรายการ (charge) ของการจองนั้นรายการเดียว เงินเข้า Opn แล้ว
Opn รู้ว่าเป็นของรายการไหน → server ถามผลจาก Opn ได้ทุกเมื่อ

1. หน้าชำระเงินเลือก PromptPay QR → กด "สร้าง QR พร้อมเพย์" → `POST /api/bookings/:id/pay` `{ method: 'promptpay' }`
   server สร้างรายการที่ Opn (`source[type]=promptpay` · `expires_at` = เวลาหมดอายุของ QR) บันทึก `payments` สถานะ `Pending`
   → COMMIT แล้วค่อยดาวน์โหลดรูป QR จาก Opn (ไม่ถือล็อกการจองระหว่างรอรูป) ตอบ `{ qr: { image, expiresAt, amount } }`
   (รูปเป็นโปสเตอร์ Thai QR Payment แนวตั้ง — โหมดทดสอบมีแถบ TEST MODE ทับ)
2. ลูกค้าสแกนจ่ายด้วยแอปธนาคาร (โหมดทดสอบ: สแกนจริงไม่ได้ → dashboard ของ Opn: Charges → รายการนั้น → Actions → Mark as successful / failed)
3. ระหว่างแสดง QR หน้าเว็บเรียก `POST /api/bookings/:id/pay/verify` `{ method: 'promptpay' }` ทุก 4 วินาที → server ถาม Opn ด้วย secret key
   → จ่ายแล้วเข้า `applyGatewayCharge()` ตัวเดียวกับ TrueMoney → การจองเป็น `Paid` → หน้าเว็บไปหน้าสำเร็จเอง
   · QR หมดอายุ/จ่ายไม่สำเร็จ → 402 (นับเป็นการจ่ายพลาด) หน้าเว็บเอา QR ออกให้กดสร้างใหม่
4. ลูกค้าปิดหน้าเว็บไปก่อนก็ได้ — ตอน deploy จริง webhook (ขั้นที่ 4 ของ TrueMoney) อัปเดตการจองให้

จุดที่ต้องอธิบายได้ตอนพรีเซนต์:
- **QR หมดอายุก่อนหมดเวลาถือห้อง 1 นาที** (`promptpayExpiry()` ใน `lib/opn.js`) — Opn ไม่รับเงินหลัง `expires_at` และ**ยกเลิก QR กลางทางไม่ได้**
  จึงต้องกำหนดตั้งแต่ตอนสร้าง: ลูกค้าจ่ายวินาทีสุดท้ายของ QR ระบบยังมีเวลา 1 นาทีรับผลก่อนห้องถูกปล่อย · เหลือเวลาถือห้องไม่ถึง 2 นาที → ไม่สร้าง QR (409)
- **Opn คืนเงิน PromptPay ไม่ได้** (เอกสารของ Opn) → `opnCanRefund('promptpay') = false`
  - ยกเลิกการจองที่จ่ายแล้ว: `cancelBooking()` ข้ามการสั่งคืนที่ Opn (ถ้าสั่ง Opn ตอบ error แล้วยกเลิกไม่ได้เลย) → บันทึกว่าคืนเงิน
    และหน้าเว็บเตือนให้โอนคืนเอง (`payment.manualRefund` ที่ server ส่งมา — แบบเดียวกับ PromptPay เงินจริงข้อ 13)
  - เงินเข้าหลังการจองไม่ได้รอชำระแล้ว (ยกเลิกระหว่างลูกค้ากำลังสแกน / จ่ายด้วยบัตรไปแล้วในอีกแท็บ) → บันทึกว่าคืนเงิน ตอบ 409 บอกลูกค้า
    และ log เลขการจอง + เลขรายการของ Opn ไว้ให้ผู้ดูแลโอนคืน (ไม่มีข้อมูลส่วนตัว)
- **กดสร้าง QR ซ้ำ / สองแท็บกดพร้อมกัน ได้รายการเดียว** — หารายการ `Pending` ของวิธีเดียวกันใต้ล็อกแถวการจอง มีแล้วส่ง QR เดิม
- **verify ระบุวิธี** (`{ method }`) — ลูกค้าสลับไปมาระหว่าง TrueMoney กับ PromptPay ได้ หน้า PromptPay ต้องตรวจรายการ PromptPay
  ไม่ใช่รายการล่าสุดของการจอง · ตัวนับ rate limit ของ verify แยกจากการกดจ่าย (30 ครั้ง/นาที — ถามทุก 4 วินาที = 15 ครั้ง)
- **รูป QR** (`downloadQrImage()`): ขอเป็น PNG ด้วย `source[qr_settings][image_type]=png` (~40 KB · ถ้าไม่ระบุได้ SVG ~225 KB)
  · ลิงก์ดาวน์โหลดมีรหัสสุ่มในตัว เปิดได้โดยไม่ต้องใช้ key (Opn ส่งต่อไปที่ไฟล์บน Amazon S3) → server **ไม่แนบ secret key**
  · ลิงก์มาจากข้อมูลที่ตอบกลับ → ดึงเฉพาะลิงก์ของ `https://api.omise.co` · ตรวจไบต์ว่าเป็นรูปจริง · ส่งให้หน้าเว็บเป็น data URL
  (เบราว์เซอร์ลูกค้าไม่ต้องต่อ Opn เอง)
- ยอดต่อครั้ง ฿20–฿150,000 (ข้อจำกัดของ PromptPay ที่ Opn) ตรวจก่อนส่ง

ทดสอบ: `node server/test/payment-methods.js` — ตั้ง key ทดสอบแล้ว: ได้รูป QR · QR หมดอายุก่อนเวลาถือห้อง · กดซ้ำได้ QR เดิม · ยังไม่จ่าย = pending
→ สคริปต์จำลองว่าลูกค้าจ่ายด้วย `mark_as_paid` ของ Opn (เฉพาะ key ทดสอบ) → การจองเปลี่ยนเป็นชำระแล้วเอง → ยกเลิกได้โดยไม่เรียกคืนเงินที่ Opn
(ไม่ตั้ง key = ทดสอบแบบจำลองเหมือนเดิม) · ลองกับ Opn โหมดทดสอบจริงในเบราว์เซอร์แล้ว: QR ขึ้น · Mark as failed → "PromptPay ประมวลผลไม่สำเร็จ"
ให้สร้าง QR ใหม่ · Mark as successful → หน้าเปลี่ยนเป็นจองสำเร็จเองภายในไม่กี่วินาที

## 13. PromptPay เงินจริง (เฉพาะผู้ดูแลระบบ · admin กดยืนยันรับเงินเอง)

ตั้ง `PROMPTPAY_ID` (หมายเลขพร้อมเพย์ที่รับเงิน — แนะนำเบอร์มือถือ) ใน `server/.env` / `.env.production` = เปิด · เว้นว่าง = ปิด
เปิดแล้ว **เฉพาะบัญชี admin** เห็นตัวเลือก "PromptPay เงินจริง (admin)" ในหน้าชำระเงิน · ลูกค้าทั่วไปยังจ่ายแบบจำลองเหมือนเดิม
(เว็บเป็นโรงแรมสมมติ — ถ้าเปิดให้คนทั่วไปโอนเงินจริงจะเสี่ยงเป็นการหลอกรับเงิน)

1. `GET /api/bookings/:id/promptpay-qr` (admin + การจองของตัวเอง + ยังรอชำระ) → server สร้าง**ข้อความใน QR**ตามมาตรฐาน
   EMVCo / Thai QR Payment เอง (`server/src/lib/promptpay.js`) แล้ววาดเป็นรูปด้วย library `qrcode`
   - ข้อความ = ชุดของ TLV (tag 2 หลัก + ความยาว 2 หลัก + ค่า): 00 รูปแบบ · 01 "12" = QR ใช้ครั้งเดียวมียอด · 29 บัญชีพร้อมเพย์
     (AID `A000000677010111` + เบอร์ `0066…`) · 58 TH · 53 764 (บาท) · 54 ยอด · 63 CRC-16/CCITT ของข้อความทั้งหมด
   - ตรวจกับตัวอย่างที่เผยแพร่ทั่วไปแล้วได้ผลตรงกัน (000-000-0000 · 4.22 บาท → CRC `E469`)
   - **ยอดเงินมาจาก server** (ยอดของการจอง) หน้าเว็บกำหนดเองไม่ได้ · หน้าเว็บโชว์เบอร์แบบปิดบางส่วน (081-xxx-5678)
2. admin สแกนจ่ายด้วยแอปธนาคารหรือแอป TrueMoney (สแกนจ่ายพร้อมเพย์ได้) → เงินเข้าบัญชีที่ผูกกับเบอร์นั้นตรงๆ ไม่มีค่าธรรมเนียม
3. ธนาคาร**ไม่แจ้งผลกลับมาที่เว็บ** (อยากให้ระบบตรวจเงินเข้าเอง → PromptPay ผ่าน Opn ข้อ 12)
   → admin เปิดแอปธนาคารของบัญชีที่รับเงิน ดูว่าเงินเข้า แล้วติ๊ก + กด "ยืนยันว่าได้รับเงินแล้ว"
   → `POST /api/bookings/:id/pay` `{ method: "promptpay_live" }` ใช้ทางเดียวกับการจ่ายแบบอื่น: 🔒 ล็อกแถวการจอง + ตรวจว่ายังรอชำระ
   (กดยืนยันซ้ำ/หลังหมดเวลาถือห้อง 15 นาที ไม่ได้) · ไม่ใช่ admin หรือไม่ได้ตั้ง `PROMPTPAY_ID` → 403 (ไม่นับเป็นการจ่ายผิด)
4. ยกเลิกการจองที่จ่ายแบบนี้ → ระบบ**โอนคืนเองไม่ได้** (ไม่ผ่าน gateway) ฐานข้อมูลบันทึกว่าคืนเงิน และหน้าเว็บเตือนให้โอนคืนเอง

ทดสอบ: `node server/test/promptpay.js` — ส่วนข้อความใน QR + ลูกค้าใช้ไม่ได้ (403) รันได้เสมอ · ส่วน admin โอน/ยืนยัน
ต้องให้ server ตั้ง `PROMPTPAY_ID` ไว้ (ไม่ตั้ง = SKIP) — ลองกับเบอร์ปลอมได้ แต่**ห้ามสแกนจ่ายจริงกับเบอร์ที่ไม่ใช่ของตัวเอง**
